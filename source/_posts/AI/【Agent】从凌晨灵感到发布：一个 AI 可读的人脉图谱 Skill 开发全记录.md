## 背景

凌晨，突然意识到一个问题：认识的所有 OI 圈朋友、初中高中同学，他们的信息全散落在各个软件里。大部分人不记得手机号或者没有加 QQ 微信，甚至不知道真名。社交软件的备注只能写几个字，塞不下这个人和我关系多好，在什么关键时刻能帮我什么。

更关键的是，AI 读不到这些信息。当对话中提到「ICPC 打星」时，它不会自动想起某位教练可以帮我争取的名额；提到「北京面基」时，它不知道我有三个朋友在北京。

我需要一个 AI 可读的通讯录。不是存电话号的那种——是存「关系网络」的那种。

## 开发过程

### 1. 数据模型设计

让 AI 完成了数据模型设计，核心字段围绕一个目的：让 AI 认识我的朋友，并在有实际需求的时候想到对应的人或许可以帮忙。

```yaml
nickname: ""       # 怎么称呼（主键）
platforms:         # QQ / 微信 / B站 / 洛谷 / CF
identity: ""       # 学校 / 年级 / 专业 / 角色
context: ""        # 怎么认识的
strength: ""       # 关系强度
help_areas: []     # 可帮事项（AI 联想核心）
trigger_tags: []   # 触发标签（wiki-link 格式）
notes: ""          # 关系边界、注意事项
```

和传统通讯录的区别：传统通讯录只存「姓名 + 电话」，这里每个联系人是一份结构化的社交画像，标签是机器可解析的触发词。

> 上面是第一版模型。这套键名后来被实践推翻了一半——v1.3 的收敛结果见后文「发布之后」。

### 2. 独立 Obsidian Vault 架构

决定把 vault 放在独立目录，与博客完全隔离。原因很实际：联系人数据含平台 ID、个人背景等敏感信息，混在博客里万一误发出去就麻烦了。

目录结构经过两次迭代：

```tree
~/people/
├── README.md          # 使用约定与设计决策
├── INDEX.md           # AI 优先读的速查索引
├── .trash/            # 安全归档（不用 rm）
├── contacts/          # 每人一个 .md
├── templates/
│   └── contact.md
└── tags/
    ├── school/        # 学校标签
    ├── field/         # 专业方向标签
    └── city/          # 城市标签
```

INDEX.md 是 AI 的入口——里面有联系人总览表 + 三层标签导航表，AI 匹配时先查这里。

### 3. 联系人批量录入

逐条从聊天记录中提取信息，一口气录入了一批联系人，覆盖竞赛圈前辈、学弟、同学、老师等多个圈层。

录入过程中有一个原则被明确下来：**主要录入「关系不深但潜在高价值」的人**。很熟的人都在脑袋里，知识库的核心价值是 AI 帮你记住那些半熟人。对于关系边界明确的人，备注里直接写「只能问简单问题，不能欠人情」。

### 4. 标签体系的三次重构

这是整个构建过程中迭代最多次的部分。

**第一版：组合标签。** 把学校和专业方向拼在一起，如「A 大学 数学」「B 大学 计算机」。建完后跑 Obsidian 图谱，发现标签之间全连成了大杂烩——两个标签因为共享一个联系人就被强制关联，两个数学专业的朋友反而没有共同标签，图谱毫无结构美感。

**第二版：两层原子化。** 拆成 `tags/school/` 和 `tags/field/`，不要组合。旧文件移入 `.trash/`。

**第三版：加城市层。** 另开 `tags/city/`。最终三层体系：

| 层 | 目录 | 边规则 |
| --- | ------------ | ------------------ |
| 学校 | tags/school/ | 学校 ↔ 城市（双向结构边） |
| 方向 | tags/field/ | 同体系可连（如 OI ↔ ICPC） |
| 城市 | tags/city/ | 同区域相邻城市可连 |

**图谱净化是关键一步。** 两个标签仅因共享联系人而相关的边是「无用边」，应该删除。比如「兰州大学」和「大学生数学竞赛 CMC」不该直接连——走 [刘适禛](https://mp.weixin.qq.com/s/4QFloR5b0O3kZOe40rW5Bg) 作为桥梁才对。脚本跑完后删了大量冗余边，最终结构边只保留学校↔城市、同体系方向、相邻城市，图谱从一团乱麻变成了清晰的层级结构。

### 5. 图谱审计脚本（audit_graph.py）

写了一个 Python 脚本来做自动化审计，因为手动检查数百条 wiki-link 太容易出错，让 Agent 查也是这样。

初版脚本做了五件事：

- **Wiki-link 解析**：正则匹配 `[[目标|别名]]`、`[[目标#锚点]]` 等四种格式
- **断链检测**：所有 `[[...]]` 目标是否都有对应文件
- **孤立节点发现**：没有标签的联系人 / 没有联系人的标签
- **冗余边识别**：标签对仅通过联系人相连的，标记为冗余候选
- **圈层分析**：每个联系人输出 `学校层 + 方向层 + 城市层` 的综合画像

### 6. 从个人工具到可发布的 Skill

录完联系人后，回头看这个过程——从零建 vault、设计标签体系、图谱净化、写审计脚本——是一套完整的、可复用的方法论。于是做了三件事：

**脱敏**：把所有个人标识替换为通用占位符，只留结构和流程。

**打包为 Skill**：核心方法论文档（SKILL.md）+ 两个模板资产（联系人模板、索引模板）+ 虚构人物的完整 onboarding 示例 + 审计脚本。通过官方打包脚本验证。

**安全审计发布**：推送 GitHub 后，用安全审查工具做了完整审计。结论 Benign——无远程下载、无自动执行、无凭证泄露。顺便试用了一下 WorkBuddy 的智能体邮箱功能，直接把打包好的 zip 作为附件发给了一个初中同学——从打包到发送全程不用离开对话界面，比手动开网页邮箱快多了。

已发布到 SkillHub 市场：[relationship-graph](https://skillhub.cn/skills/indiv-zaochen/relationship-graph)

## 发布之后：三次版本迭代（v1.1 → v1.3）

发布不是终点。上大学后，我自己电脑上的人脉库一路从十几个联系人长到 55 人 / 5 份名单 / 64 个标签，每一次版本演进都是被真实使用中的摩擦推着走的。

### v1.1：中文化 + schema 收敛

全库文档中文化；数据模型收敛为「7 个 YAML 键 + 4 个正文小节」——`help_areas` / `trigger_tags` / `notes` 不再是 YAML 字段，改由 `## 可帮事项`、`## 触发标签`、`## 历史互动`、`## 备注` 四个正文小节承担，YAML 只留真正结构化的东西。审计脚本同步获得解析正文 `yaml` 围栏块的能力，并修掉了模板注释里占位双链被当成真实链接的「幽灵边」。

### v1.2：第三种实体——名单（roster）

联系人库解决了「这个人是谁」，但还有一大片灰色地带：班级、竞赛队里只有一张名单之交的人——没登记联系方式，但找人时依然有效（「哪些同学选了这门课」这句话，光靠联系人答不上来）。

v1.2 加了 `rosters/`：一份名单一个文件，成员表格 `姓名 | 角色 | 状态`。已登记成员用 `[[双链]]` 直达人脉档案；仅名单成员只有名字和角色，不建文件。话题命中名单的「触发场景」时浮现整份名单；名单的增删**不往回写联系人文件**——成员关系的唯一事实源就是名单本身。

### v1.3：审计自动化 + 数据规范 v2

这版的导火索是，我拿审计脚本去跑真实 vault，输出 **0 issues**；再人工核对加只读原型逐项检查，实际存在 **64 个真实缺陷**。脚本不是瞎写——它检查的（双链目标、孤立节点、冗余边）确实都对——但它只会查「显式损坏」，索引层与语义层的所有数据漂移都不在它的职责里。0 issues ≠ 没问题，这是审计工具最危险的一种失败。

**审计工具补上的检查**（每条都对应真实库里抓到的坏例）：

| 类别 | 抓什么 |
| --- | --- |
| INDEX 对账 | 两行误并成一行的坏行、联系人缺行、名单计数过期、导航行指向不存在的文件、触发标签格落后于档案 |
| 标签页成员双向核对 | 52 处「联系人挂了标签、标签页没列他」——直接削弱触发式召回；反向漂移逐例人工定方向 |
| YAML schema | 解析失败不再被 try/except 静默吞掉——一处引号嵌套能让整块字段从所有检查里隐身 |
| 平台 ID 碰撞 | 同一 QQ 号 / 学号出现在两个档案（把「冲突先问」里最常见的一种机械化） |
| last_contact | 非日期值、未来日期、超 90 天未联系——**只报告，绝不替人改日期** |
| 名单状态机 | 新增第三状态「本人」；成员节判定改为「节名在首个括号前含『成员』」，`## 分工线（…主要成员介绍…）` 这类诱饵标题不再被误当成员表 |

**数据规范向现实投降**：

- `platform`（单数）/ `met` 扶正——54/55 个文件实际早就这么写，规范定的 `platforms` / `context` 只有第一个人遵守，于是统一了一下；
- 新增 `platform.qq_nickname` / `wechat_nickname` 昵称子键。动机是一起识别事故：档案只记了 QQ 号没记昵称，聊天记录里对方以昵称出现，AI 认不出来、当成陌生人重新分析了一遍。教训「要连昵称一起记」当初只写在了那人的备注里，模板却没改——这次把它变成结构字段和审计提示，散落各处（YAML 注释、`other` 文案、QQ 号值里的括号注释）的昵称全部统一归宿；
- `strength` 从英文枚举改为**自由词、零校验**：55 个文件只有 1 个用枚举，实际写的是「恩师」「刚建联」「最最好的朋友（QQ 置顶）」。枚举已死，与其留着死规范，不如给一份仅参考的中文词表；
- INDEX 第 2 列收编为「缩写·网名」检索列（拼音首字母 + 空格分隔网名）——不加新列，把已经发生的使用习惯扶正，处理聊天记录检索昵称优先命中这里；
- 名单计数规范形 `N 已登记 / M 仅名单（另含本人）`，审计逐份核对。

**方法论沉淀**：

- 聊天记录处理：步骤 0「先识别身份，再解读内容」——拿到任何群聊记录，先全库 grep 每个昵称 / QQ 号确认谁已入库；QQ 截图附件要下载下来真做视觉识别，截图的信息量常常大于文字层；
- 导入版式：`## 2026-10-23 · 主题` + `> 来源` + `谁 | 原话` 逐字表，放联系人文件末尾按日期升序；引用原话保留原始措辞；
- **批量补全的保真原则**：这次重构是 AI 批量脚本干的，翻车方式很典型——把标签页里人工精选的语境行覆盖成从 `identity` 字段硬截断的通用串（切出半截括号、半截英文 handle）。由此立了四条规矩：不覆盖人工评注、截断宁可长不可断、删散键必须把信息迁进备注、改完必扫 git diff。一句话：**审计保证「没错」，diff 保证「没退化」**——审计抓不到语义倒退。

**工程化**：

- 审计脚本配了 28 例单元测试（stdlib unittest + tempfile 构造迷你 vault），每个易误报的解析路径都有 fixture 钉住；
- 缺 pyyaml 时**诚实降级**为纯结构审计并显式声明，`--strict` 在降级模式直接拒绝运行——门禁不能半盲亮绿灯；
- 发布版与安装版允许有意差异：发布仓库里示例全部虚构、删掉了「旧键名容忍」这类历史包袱机制（发布版面向新用户，没有迁移动机）；本地安装版保留容忍，伺候真实库的异类文件。

还有个有意思的流程细节：v1.3 的两处早期修复其实先落在**本机安装的 skill 副本**上实弹试跑（安装版领先了仓库版一个多月），发布时再回灌进仓库——「安装版跑在前、发布版收在后」大概就是 skill 这种形态的正常迭代节律。

重构后的真实库复审：**64 错误 → 0**，剩余 22 条提示全是合法残留（陈旧联系、待补信息之类，报告给人类自己决定）。

## 关键决策

1. **独立 vault，不混博客**：联系人含敏感信息，隔离是底线
2. **半熟人优先录入**：很熟的人在脑子里，AI 帮我们记住的是「目前关系不深但潜在高价值」的人
3. **三层原子标签 + 联系人桥接**：标签不搞组合，不同圈层的连接通过联系人节点自然形成
4. **图谱净化：人是桥，标签不过度互联**：删除仅共享联系人而存在的标签边，让图谱从大杂烩变成有结构的网络
5. **冲突先问，不猜**：疑似重复、信息矛盾时不自动合并/覆写，先展示给用户确认
6. **审计脚本不是摆设**：数百条 wiki-link 的手动审计不可靠，一个脚本跑完比肉眼准
7. **工具拿真库验收**：审计对真实库报 0 issues 时，先怀疑工具再相信数据；每条检查都得有已知坏例做回归测试，否则它只是在表演检查
8. **规范向实践投降**：键名、强度词表这类约定被 54/55 的文件无视时，错的是规范——收编现实，不要留着死规范丢面子
9. **机器批量写必须过 diff 人眼**：审计能抓「错」抓不到「退化」，人工评注被截断串覆盖就是退化
